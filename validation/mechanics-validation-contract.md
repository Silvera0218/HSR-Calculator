# 全实战机制：独立模型验收合同

状态：**BLOCKED（模型预检）**。用户目标为所有角色、E0–E6、光锥、遗器和行迹的实际战斗效果及交互优化。当前只有拟定事件名称，尚未提交逐效果规则映射、事件优先级来源和候选战斗核心，不能批准“全机制已实现”。现有 Excel 1.2 的固定条件 PASS 继续只适用于原范围。

本文件为候选核心的验收要求，不是官方战斗顺序说明。下述建议中的顺序若影响结果，必须由绑定的技能/效果来源或可核验实验确认；未知处标 `unsupported`，不能靠统一默认假设声称覆盖。

## 1. 最小必要状态

| 所属模块 | 必需状态 |
|---|---|
| 战斗 | 时间/行动距离；有序事件队列；battleId；版本及来源快照；事件序号；随机算法/种子/抽样索引；模式；停止原因 |
| 实体 | entityId、ownerId、阵营、位置/相邻关系、角色与形态、等级、存活/退场/复活、基础属性和属性来源；动态属性缓存版本 |
| 生存 | 当前/最大 HP；有序护盾实例及容量、来源、类型、到期方式；伤害承受修正；治疗/受治疗修正；生命消耗地板及致死策略 |
| 时间线 | 当前行动距离、基础距离、实际速度；行动提前/延后；额外行动；正常回合与额外行动的区分；独立倒计时实体 |
| 资源 | 队伍 SP 及上限；实体能量及上限；固定/普通回能标记；角色专属资源、层数、充能；每回合/每行动触发次数 |
| 韧性 | 每目标最大/当前韧性、属性弱点、无视弱点削韧比例、击破状态与恢复规则；虚韧性实例；击破者及来源 |
| 效果实例 | effectId、ruleId、sourceEntityId、targetEntityId、叠层、独立实例/刷新策略、上限、施加事件、到期事件和到期锚点、属性/伤害标签、快照或动态读取 |
| 召唤物 | entityId、ownerId、属性继承/转换关系、独立时间线、技能、生命周期、消失/替换、能量与召唤物资源；不可只当额外倍率 |
| 行动 | actionId、parentActionId、行动类型/标签、技能形态及等级、目标选择、逐段 hit 计划、每段倍率/削韧/回能/附着、成本、锁定/动态取值方式 |
| 触发追踪 | causationId、触发祖先链、事件来源、可反应标签、重入/同类触发策略；禁止使用全局“追加不能触发追加”代替逐规则限制 |

数组位置和角色 id 不可代替实体 id。相同角色来源的多个召唤物、多个状态和相同时间的事件要能区分。

## 2. 事件与更新顺序

每一条规则都必须声明订阅事件、执行优先级及读取的快照。建议队列排序使用 `(time, resolutionPhase, sourcePriority, insertionSequence)`；所有并列依据可追溯，不能让对象遍历顺序决定结果。

1. `BattleStart`：建立实体与召唤物、应用常驻效果、执行入战效果、重算派生属性、排时间线。入战前/入战后属性门槛和秘技需独立时点。
2. `TurnStart`：确定到达的是正常回合、额外行动或倒计时；按规则执行 DoT、恢复韧性、控制状态、开始时到期/刷新。DoT 与恢复先后须明确来源。
3. `BeforeAction`：检查存活、控制、合法目标、形态、技能可用性和资源；确定最终技能及成本；用对应资源规则支付。失败不得消耗或刷新未声明的状态。
4. 构造 action 的逐段逐目标计划。随机弹射目标、相邻目标、锁定/动态目标必须独立表达。AOE 命中每个目标的记录不能混成一个全局 hit。
5. 每段 `BeforeHit → ResolveHit → Hit/AfterHit`：确定目标仍有效，读取声明的属性快照，结算随机结果、伤害、护盾/HP、削韧、附着和回能。各写入阶段分别保存 before/after 值。破韧、击杀、受伤害是明确子事件，触发先后按该技能规则；不能未经证据把所有技能统一成“先破韧后伤害”或“先伤害后破韧”。
6. `Break`：只在正韧性穿越到 0 时触发一次；记录该段和击破者。后续段读取新的破韧状态。初始击破、击破后状态、超击破、虚韧性、延后与恢复分别处理。
7. `DamageTaken`：至少携带 preShieldDamage、shieldAbsorbed、hpLoss、damageDealt、damageChannel、hit/action 标签；来源明确消耗生命时必须区分 `HpCost`，不得自动视为受攻击。
8. `Kill/Death`：声明与 Break、AfterHit 的次序及结算边界；取消或重定向后续 hit、复活、召唤物退场、击杀回能和队友响应分别处理。反伤导致双方死亡不能被先遍历者覆盖。
9. `AfterAction`：行动型触发只运行一次；按命中记录读取多目标/多段效果，消耗“下次攻击”实例，执行行动后回能/治疗/转化。追加与终结技请求进入队列。
10. `UltQueue`：能量达标是请求资格，不代表立即在任意阶段插入。队员顺序、手动请求、自动策略、可打断窗口和资源锁定必须声明。终结技是独立 action，不把其 damage/SP/削韧直接并进主 action 的一个 hit。
11. 追加/FUA、反击、忆灵及欢愉行为按规则成为独立 action 或附加 hit。执行优先级、是否消耗正常回合/行动距离、可触发哪些规则必须单独声明。
12. `TurnEnd`：按效果到期锚点递减或移除；重新计算下一行动距离。禁止所有 buff 在任意实体 TurnEnd 统一减一。

推荐明确新增 `BeforeHit、EffectApplied、EffectExpired、HpCost、ResourceChanged、EntitySpawn、EntityRemoved、Advance、Delay`。若核心使用等价内部操作，也必须具有同等日志和规则定位能力。

## 3. 状态有效期、派生属性和时间线

- duration 必须同时指定时钟：持有者正常回合、施放者回合、目标回合、行动次数、攻击次数、受击次数、时间线倒计时，或本次行动结束。
- 写明效果在施加当回合是否计数、开始/结束过期、刷新是否保留旧剩余次数、叠层是整体到期还是逐层到期。不能只保存 `duration: 2`。
- 属性转换明确 source stat、可转化部分、读取时点、上限、叠加组及循环依赖策略。像效果命中转攻击，不能把被转化后的量再次转化。
- 速度变化根据剩余行动距离重新排队；不能直接重置剩余行动值为 `10000/newSpeed`。提前/延后也操作剩余距离，越界策略明确。
- 追加/终结技/额外行动是否推进该实体正常时间线是规则属性。召唤物、神君和状态倒计时均可有独立时间线。
- 多段攻击越过击破点后，下一段必须重新读取击破态；同一事件开始状态用于所有段的旧固定条件简化不适用于完整实战。
- 技能伤害、DoT、击破后 DoT、欢愉、真实伤害、治疗、护盾是不同 channel；源属性和“已结算伤害”转换不得重复应用公共乘区。

## 4. 确定性和随机语义

建议完整实战默认采用固定 seed 的随机轨迹。相同输入、规则版本、seed、随机算法应得到相同完整事件日志。用户可修改 seed；平均/分位数使用多次独立轨迹，并显示试验次数与误差。

固定 seed 的可重放轨迹和“期望伤害”需要分开命名。静态伤害拉表可在冻结条件下使用期望暴击；动态模拟中，暴击、附着、随机目标、随机资源及对应触发必须实际决策，不能把概率层数、触发次数、击杀或控制状态平均化。

严格期望模式只有两种可接受实现：小状态下精确分支/DP 且保存全部概率质量，或足量 seeded Monte Carlo 并标抽样统计。所有依赖条件的效果保留相关性，禁止对各项概率独立均摊后判断门槛。

SymPy 合成反例已核验：每次独立 50% 概率增加 1 层，达到 2 层触发，在 2 次尝试后实际触发概率 `1/4`。把每次增加 0.5 层均摊后只得到 1 层，会错误地报告永不触发。三状态矩阵 `[[1-p,p,0],[0,1-p,p],[0,0,1]]` 的两步概率质量合计为 1。

抽样记录保存每个 decisionId、概率、rawDraw、结果、关联 action/hit/target。顺序 RNG 要声明新增规则导致抽样序列改变；比较配置可使用基于稳定 decisionId 的分流 RNG，不能隐含声称抽样独立。确定性测试可注入规定抽样结果，但该模式属于测试，不作为真实期望值。

## 6. 每条效果的覆盖验收

每个效果规则至少记录：

```text
ruleId, sourceKind, sourceEntityId, version/snapshot,
sourceFile, sourceHash, jsonPointer, descSpan/predicateSpan,
parameterPointers, levelOrSuperimpositionSelector,
characterForm, eidolonApplicability, traceUnlock,
event, priority, condition, targetSelector, operation,
durationClock, refreshStackPolicy, damageTags,
implementationRef, tests, supportStatus, reason
```

`supportStatus` 仅使用 `verified / implemented_unverified / unsupported / source_missing / not_applicable`。有正文无执行规则是 `unsupported`；参数缺失是 `source_missing`；未测试不是 `verified`。

- 覆盖单位是语义效果、谓词和参数，不能按文本条数、角色数、文件数或“关键词识别成功”计算完成。复合正文必须拆出每个成本、伤害、附着、目标、触发、持续时间、上限及例外；同一规则可绑定多个明确源片段。
- 每个源正文片段和参数均有规则映射或具原因的 source gap。移除格式字符、物品背景文案等非战斗内容也要列可审计排除类型；不能按字符覆盖声称语义已验证。
- E0–E6 是累计解锁；每个角色形态至少有七个配置分支的结构审查，以及每条星魂的 unlock-before/unlock-after 差分用例。技能加级另检查训练上限，不能直接使用源参数数组的 15 级上限作为训练满级。
- 光锥逐叠影参数 S1–S5 有映射与命途匹配/不匹配用例；遗器 0/2/4 件数、散件、混搭、属性门槛与触发持续条件分别验收；行迹等级/突破门槛及技能形态必须显式。
- 命途、角色、召唤物、来源转化的过滤条件不能只作为 UI 文案。执行轨迹必须显示规则命中/未命中的原因。
- 只有所有适用效果 `verified` 且无未映射片段、未映射参数、unsupported/source_missing，才可声称所定义版本全效果支持。针对选定队伍可出局部 PASS，但名称明确范围。
- 若用户选定的队伍包含 unsupported，运行前显示具体角色/光锥/套装/星魂和缺失规则；用户可运行已标注的部分模型，结果必须携带 incomplete 状态。不能在 UI 隐藏失败或给出完整战斗结论。

## 7. 候选核心的最小独立校验包

需交接模型版本/内容 hash、effect coverage manifest、事件顺序、单位/上限/取整、随机算法/seed、固定输入、完整事件日志。此阶段不要求游戏体验平衡或额外 UI 改造。

必须包含：

1. 一个纯普通攻击无触发基线；一个多段越过击破点且后续段使用新状态的用例。
2. shield 耗尽、真实 HP 损失、生命消耗地板、治疗截顶、受治疗加成；至少一个 damage-based trigger 区分 shieldAbsorbed/hpLoss。
3. source-turn/target-turn/next-attack 三种有效期，新增当回合计数、刷新/独立层到期。
4. 速度变化、提前 0%/100%、延后、同刻并列、独立召唤物/倒计时、终结技合法插入窗口。
5. FUA 链、反击、触发限制、死亡取消后续段、随机弹射目标；终结技/额外行动不误推进正常回合。
6. DoT 附着成功/失败、层数与刷新、动态/快照读取、引爆不重复抽附着；击破 DoT 与普通 DoT 分离。
7. 种子重放逐事件相同；0/1 概率边界；小状态分支概率与 SymPy 精确矩阵一致；Monte Carlo 抽样误差与理论可解释。
8. 每条角色/星魂/光锥/套装/行迹规则的正触发、负触发、边界/上限用例。不能拿以上公共能力用例替代全规则覆盖。

下一允许状态：提交候选核心及上述规则 manifest 后进行公式/状态子系统验证；缺少来源规则时保持 BLOCKED，全效果完成门不得通过。
